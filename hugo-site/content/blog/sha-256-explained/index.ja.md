ダウンロードページの末尾にある64文字の16進数——SHA-256チェックサム——ほど、頻繁に目にされ、理解されていない数字はありません。それはファイルの指紋であり、Bitcoinのプルーフ・オブ・ワークのエンジンであり、すべてのGitコミットの識別子であり、無数のWebhook署名の検証層です。そして同時に、人々が「別のもの」を選ぶべき場面で手を伸ばす答えでもあります——SHA-256でパスワードをハッシュすることは、いまなお新規コードで見られる最も一般的なセキュリティミスの一つです。

本ガイドでは、SHA-256が実際に何をするのか、ハッシュと暗号化・エンコードの区別、このアルゴリズムが正しい道具である場面と誤った道具である場面を解説します。サードパーティコードなしでブラウザ内生成するなら、当サイトの無料[SHAハッシュジェネレーター](/ja/tools/hash-generator/)を。

## ハッシュ関数とは

暗号学的ハッシュ関数は、3つの決定的性質を持つ一方向関数です：

1. **決定的。** 同じ入力からは常に同じ出力が得られます——今日も、このコンピューターでも、他のどんなコンピューターでも
2. **固定長出力。** 入力が1文字でも1テラバイトでも、SHA-256は正確に256ビット（32バイト、16進数64文字）を返します
3. **雪崩効果。** 入力の1ビットを変えると出力ビットの約半分が反転します。出力から入力へ「逆算」する方法はなく、唯一の攻撃は総当たりです

これらの性質が、ハッシュを理想的な**整合性の指紋**にします。ファイルを保存せずとも、64文字の文字列を比較するだけで改ざんの有無を検証できます。

## SHAファミリーの略史

SHAはSecure Hash Algorithmの略で、米国標準技術研究所（NIST）が公開しています。関連する系譜：

| アルゴリズム | ダイジェスト長 | 2026年の位置づけ |
|-------------|--------------|----------------|
| MD5 | 128ビット | 破綻——衝突が実用的。絶対に使わない |
| SHA-1 | 160ビット | 実用上破綻（SHAttered、2017年）。レガシーのみ |
| SHA-256 | 256ビット | 標準——デフォルトの選択 |
| SHA-512 | 512ビット | 標準——64ビットCPUで高速、ダイジェストは長め |
| SHA-3／BLAKE3 | 可変 | 現代的代替。まだ普及途上 |

実務の指針は1行に収まります。**特別な理由がない限りSHA-256を使う。** 高速で、どこでもサポートされ、実用的な衝突攻撃は知られていません。

## ハッシュ vs 暗号化 vs エンコード

この3つは絶えず混同され、その違いが道具選びを決めます：

| | 目的 | 鍵 | 可逆性 | 例 |
|---|---|---|---|---|
| **エンコード** | 別形式で表現 | 不要 | 常に可逆 | Base64、16進数、UTF-8 |
| **暗号化** | 機密性 | 必要 | 鍵があれば可逆 | AES、ChaCha20 |
| **ハッシュ** | 整合性・指紋 | 不要 | 不可逆（一方向） | SHA-256 |

判断ルール：元に戻す必要があるデータ→暗号化。*認識*できればいいデータ→ハッシュ。テキスト経路を無傷で通したいデータ→エンコード（[Base64ガイド](/ja/blog/base64-encoding-explained/)参照）。「誰かが原文を再び読む必要があるか」と自問するだけで、混乱の大半は消えます。

## SHA-256が正しい道具である場面

**ファイル整合性。** 古典的用途。ベンダーがダウンロードの隣にチェックサムを公開し、あなたはダウンロード後にファイルを検証する。改ざんも——悪意あるものも単なる破損も——ダイジェストを変えます。

**コンテンツフィンガープリント。** Gitはコミットやオブジェクトを内容のSHA-1/SHA-256ダイジェストで識別します。ブロックチェーンはブロックをハッシュで連結します。コンテンツアドレス方式のシステムは内容からIDを導出するため、同一コンテンツは自動的に重複排除されます。

**パスワード検証——誤った方法と正しい方法。** `SHA256(password)` を保存するのが誤りな理由は2つ。ハッシュは高速で（攻撃者はGPUで毎秒数十億回試行できる）、同一パスワードは同一ハッシュを生む（誰が使い回しているか漏れる）。正解は**遅く・ソルト付き・メモリ困難**な関数：Argon2、bcrypt、scrypt。ソルトは同一パスワードを別々にハッシュし、意図的な遅さが総当たりを高価にします。SHA-256の速さ——他の場所では美徳——が、ここでは弱点そのものです。

**署名のためのHMAC-SHA256。** HMACはハッシュ関数を秘密鍵で包みます：`HMAC-SHA256(key, message)`。結果は整合性と「鍵を知っている」ことの両方を証明します。APIリクエスト署名とWebhook検証の標準で、Stripe、GitHub、多くのLLMプラットフォームがこの方式でWebhookに署名しています。「この署名を検証せよ」と言われたら、ほぼ間違いなくHMACです。

## SHA-256の仕組み：概観

全アルゴリズムは記事に収まりませんが、性質を説明する形は重要です。SHA-256は入力を512ビットのブロック単位で処理し、64ラウンドの圧縮関数に通します。状態は8つの固定32ビットワードから始まり、各ブロックがビット回転・加算・XORで入力を状態に混ぜ込み、最終状態がダイジェストになります。ここから2つの帰結が：

- **ストリーミング。** ブロック単位で処理するため、ファイルを逐次ハッシュできます——10GBのファイルでもメモリはほぼ使いません
- **不可逆性。** 各ラウンドが情報を破壊します（圧縮関数は多対一）。逆関数は存在せず、ダイジェストに合う入力を見つける唯一の方法は推測です

## 量子コンピューターは脅威か

量子コンピューターが脅かすのはShorのアルゴリズムによる*非対称*暗号（RSA、ECC）です。SHA-256のような対称ハッシュへの影響ははるかに小さく、Groverのアルゴリズムでもせいぜい平方根の高速化——SHA-256は仮想的な量子攻撃者に対して実効約128ビットの安全性に半減するだけで、依然として十分安全です。ハッシュに関する量子時代の実務アドバイスは今日と同じ：SHA-256（またはSHA-3）で問題ありません。移行計画が必要なのはスタックの非対称部分です。

## 実践でのチェックサム生成と検証

コマンドラインツールは普遍的で、ワークフローはどこでも同じです：生成、比較、自動化。

**生成**：

| プラットフォーム | コマンド |
|----------------|---------|
| macOS／Linux | `shasum -a 256 file.zip` |
| Windows（PowerShell） | `Get-FileHash file.zip -Algorithm SHA256` |
| Linux（別解） | `sha256sum file.zip` |
| ブラウザ／CLIなし | [SHAハッシュジェネレーター](/ja/tools/hash-generator/) |

**比較**。一度きりなら目視でも——ただし人間は64文字の16進数を比較するのが苦手で、「チェックサム不一致」が見逃される古典的原因です。堅牢な形はプログラムで比較すること：

```sh
# macOS/Linux
echo "EXPECTED_HASH  file.zip" | shasum -a 256 -c -
# -c フラグが指定行とファイルを照合し、OK/FAILED を報告します
```

**自動化。** CIでは、ダウンロードする依存関係をすべて固定ダイジェストで検証し、自前のリリース成果物の隣にもダイジェストを公開しましょう（GitHubのリリースページは自動表示します）。固定ハッシュ検証は、サプライチェーン侵害を「検出不能」から「赤いビルド」に変えます——パイプラインに追加できる単一の整合性チェックとして最も価値が高いものです。

**実例。** ベンダーが `data.csv` のダイジェスト `9f86d081...` を公開したとします。ダウンロードして `shasum -a 256 data.csv` を実行すると別の文字列が。可能性は2つ：ダウンロードが壊れた（リトライ）、あるいは改ざん・黙った再公開（停止して調査）。ハッシュは*どちらか*を教えません——約束と違うバイト列であることだけを教えます。この制約こそ設計どおりです：ハッシュは検出するのであって、裁定するのではありません。

## 新規システムのアルゴリズム選定：2026年チェックリスト

新システムでハッシュが必要になったら、このリストを一度回しましょう：

1. **パスワード** → Argon2id（またはbcrypt/scrypt）。生のSHA-256は不可
2. **ファイル整合性／フィンガープリント** → SHA-256。安定・高速・普遍的
3. **高保証・長期** → 将来の進展への余裕が欲しければSHA-512またはSHA-3-256
4. **メッセージ認証** → ランダム32バイト鍵のHMAC-SHA256——暗号化もするならAEADモード（AES-GCM、ChaCha20-Poly1305）
5. **重複排除／コンテンツアドレッシング** → コンテンツのSHA-256。曖昧性攻撃を避けるため長さプレフィックスを付ける

ミスの大半を防ぐ2つの質問：*秘密が関わるか？*（関わる→HMACかAEADであって裸のハッシュではない）と、*誰かが元データを取り戻す必要があるか？*（ある→暗号化かエンコードであってハッシュではない）。
