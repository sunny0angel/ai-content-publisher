计算世界里很少有哪个数字像下载页末尾那 64 位十六进制字符串——SHA-256 校验和——一样常见却又不被理解。它是文件的指纹、比特币工作量证明的引擎、每个 Git 提交的标识符、无数 Webhook 签名的验证层。同时，它也是人们在应该选择「别的东西」时伸手去拿的答案——用 SHA-256 哈希密码，至今仍是新代码里最常见的错误之一。

## 什么是哈希函数

密码学哈希函数是具有三个决定性性质的单向函数：

1. **确定性。** 相同输入永远产生相同输出——今天如此、这台电脑如此、任何电脑都如此
2. **定长输出。** 无论输入是一个字符还是一太字节，SHA-256 都精确返回 256 位（32 字节，写作 64 位十六进制字符）
3. **雪崩效应。** 改动输入的 1 个位，约一半输出位会翻转。不存在从输出「反推」输入的方法——唯一的攻击是暴力穷举

这些性质让哈希成为理想的**完整性指纹**：不必保存文件，比较一个 64 字符的字符串就能验证它是否被改动。

## SHA 家族简史

SHA 即 Secure Hash Algorithm（安全哈希算法），由美国国家标准与技术研究院（NIST）发布。相关的谱系：

| 算法 | 摘要长度 | 2026 年状态 |
|------|---------|------------|
| MD5 | 128 位 | 已破解——碰撞可行，永远不要用 |
| SHA-1 | 160 位 | 实践中已破解（SHAttered，2017）；仅遗留兼容 |
| SHA-256 | 256 位 | 标准——默认选择 |
| SHA-512 | 512 位 | 标准——64 位 CPU 上更快，摘要更长 |
| SHA-3 / BLAKE3 | 可变 | 现代替代品，尚未普及 |

实用指引收敛成一句话：**没有特别理由就用 SHA-256。** 它快、处处支持、没有已知的实用碰撞攻击。

## 哈希 vs 加密 vs 编码

这三者被不断混淆，而区别决定了工具选择：

| | 目的 | 密钥 | 可逆 | 示例 |
|---|---|---|---|---|
| **编码** | 用另一种形式表达数据 | 无 | 永远可逆 | Base64、十六进制、UTF-8 |
| **加密** | 机密性 | 有 | 有密钥即可逆 | AES、ChaCha20 |
| **哈希** | 完整性 / 指纹 | 无 | 不可逆（单向） | SHA-256 |

决策规则：需要还原的数据→加密。只需*识别*的数据→哈希。必须通过文本通道的数据→编码（见 [Base64 指南](/zh/blog/base64-encoding-explained/)）。问一句「将来有人需要再读到原文吗」，大半困惑就消失了。

## SHA-256 是对的工具的场合

**文件完整性。** 经典用途：厂商在下载旁公布校验和，你下载后验证文件。任何篡改——恶意的或仅仅是下载损坏——都会改变摘要。

**内容指纹。** Git 用内容的 SHA-1/SHA-256 摘要标识提交和对象。区块链用哈希串联区块。内容寻址系统从内容推导 ID，相同内容自动去重。

**密码验证——错误做法与正确做法。** 存 `SHA256(password)` 错误有两个原因：哈希太快（攻击者用 GPU 每秒能试数十亿次），且相同密码产生相同哈希（泄露谁在复用密码）。正确做法是**慢速、加盐、内存困难**的函数：Argon2、bcrypt 或 scrypt。盐让相同密码哈希出不同结果；刻意的慢让暴力破解昂贵。SHA-256 的速度——在其他地方是优点——在这里恰恰是弱点。

**用于签名的 HMAC-SHA256。** HMAC 用密钥包裹哈希函数：`HMAC-SHA256(key, message)`。结果同时证明完整性和「发送方持有密钥」。这是 API 请求签名与 Webhook 验证的标准：Stripe、GitHub 和大多数 LLM 平台都这样给 Webhook 签名。凡是「验证这个签名」的场景，你面对的几乎都是 HMAC。

## SHA-256 的工作原理（概览）

完整算法一篇博客装不下，但它的形状解释了那些性质。SHA-256 按 512 位的块处理输入，经过 64 轮压缩函数。状态从 8 个固定的 32 位字开始；每个块用位旋转、加法和 XOR 把输入混进状态；最终状态就是摘要。由此得出两个推论：

- **流式处理。** 因为按块处理，你可以增量哈希一个文件——哈希 10 GB 文件几乎不占内存
- **不可逆性。** 每轮都在销毁信息（压缩函数是多对一的），逆函数不存在。找到匹配某摘要的输入的唯一方法是猜

## 量子计算机呢

量子计算机通过 Shor 算法威胁的是*非对称*密码学（RSA、ECC）。SHA-256 这类对称哈希受影响小得多：Grover 算法最多提供平方根级加速，意味着面对假想的量子攻击者，SHA-256 的有效安全性减半到约 128 位——依然十分安全。哈希方面的量子时代实用建议与今天相同：SHA-256（或 SHA-3）没问题；需要迁移规划的是你技术栈里的非对称部分。

## 实战生成与验证校验和

命令行工具无处不在，工作流处处相同：生成、比较、自动化。

**生成**文件摘要：

| 平台 | 命令 |
|------|------|
| macOS / Linux | `shasum -a 256 file.zip` |
| Windows（PowerShell） | `Get-FileHash file.zip -Algorithm SHA256` |
| Linux（替代） | `sha256sum file.zip` |
| 浏览器 / 无 CLI | [SHA 哈希生成器](/zh/tools/hash-generator/) |

**比较**公布值。一次性下载目视也行——但人类不擅长比较 64 位十六进制字符，这正是「校验和不匹配」被忽视的经典原因。稳妥的做法是程序化比较：

```sh
# macOS/Linux
echo "EXPECTED_HASH  file.zip" | shasum -a 256 -c -
# -c 标志按给定行核对文件并报告 OK/FAILED
```

**自动化。** 在 CI 里用固定摘要验证每个下载的依赖，并在自己的发布产物旁公布摘要（GitHub 发布页会自动显示）。固定哈希验证把供应链攻击从「无法察觉」变成「构建变红」——这是流水线能加入的最高价值的单项完整性检查。

**一个实例。** 厂商为 `data.csv` 公布了 `9f86d081...`。你下载后运行 `shasum -a 256 data.csv`，得到不同的字符串。两种可能：下载损坏（重试），或被篡改/厂商静默重发（停下，调查）。哈希不会告诉你*是哪一种*——它只告诉你字节与承诺不符。这个局限恰恰是设计所在：哈希负责检测，不负责裁定。

## 新系统算法选型：2026 检查清单

新系统需要哈希时，把这张清单过一遍：

1. **密码** → Argon2id（或 bcrypt/scrypt）。裸 SHA-256 永远不行
2. **文件完整性 / 指纹** → SHA-256。稳定、快速、通用
3. **高保证、长期** → 想留出应对未来进展的余量，用 SHA-512 或 SHA-3-256
4. **消息认证** → 随机 32 字节密钥的 HMAC-SHA256——同时加密时用 AEAD 模式（AES-GCM、ChaCha20-Poly1305）
5. **去重 / 内容寻址** → 内容的 SHA-256；加长度前缀避免歧义攻击

两个问题防住大多数错误：*涉及秘密吗？*（涉及 → HMAC 或 AEAD，而不是裸哈希）和*有人需要还原原文吗？*（需要 → 加密或编码，而不是哈希）。
