Base64は、誰もが使っているのにほとんど誰も説明できない技術の代表格です。JSON Web Token、`data:` URL、メール添付、APIペイロードの途中——どこに現れても同じ混乱を生みます。*これは暗号化なのか？圧縮なのか？なぜテキストが33%増えるのか？* 答えは「暗号化でも圧縮でもない」。Base64は任意のバイナリデータをテキスト専用経路でも壊れず通すための変換層であり、33%のオーバーヘッドはその生存の代償です。

本ガイドでは、Base64が実際に何をするのか、エンコードをステップごとに追い、実システムでの登場場面を解説します。UTF-8を正しく扱う変換は、当サイトの無料[Base64エンコーダー／デコーダー](/ja/tools/base64-encoder/)で——完全にブラウザ内で動作します。

## 1分でわかるBase64

Base64は**バイナリからテキストへのエンコード**です。任意のバイト列を、64種類の表示可能なASCII文字だけで表現します。アルファベットは次のとおり：

```
A–Z（26）＋a–z（26）＋0–9（10）＋「+」「/」（2）＝64文字
```

末尾にはパディングとして `=` を使います。3バイトの入力（24ビット）が4文字の出力（4×6ビット＝24ビット）になるため、出力は常に入力より約33%大きくなります——3バイトだった場所に4文字。

エンコードは完全に可逆かつ決定的です。同じバイト列からは常に同じテキストが生まれ、有効なBase64テキストは必ず元のバイト列に正確に戻ります。この可逆性こそが本質であり、Base64が**暗号化ではない**理由でもあります。アルファベットを覚えれば、誰でも手でデコードできます。

## Base64が存在する理由：テキスト経路問題

コンピューターシステムは「バイトの意味」について驚くほど合意できません。0x89というバイト値は、ある場所では「PNGヘッダーの先頭バイト」、別の場所では「文字列を終端する制御文字」、さらに別の場所では「取り除くべきもの」です。JSON文字列、XML文書、メール本文、URLパラメータ、DBのテキスト列など、テキスト用に設計された経路は、任意のバイトが無傷で通過することを保証しません。安全範囲外のバイトを拒否したり、誤った文字エンコーディングで解釈し直したり、最初のnullバイトで止まったりします。

Base64は、すべてのバイト値を「あらゆるテキストシステムが無変更で通すことに合意している」64文字に写像することで解決します。コストはサイズ増、見返りは「送った通りに届く」ことです。

## ビット単位で見るエンコードの仕組み

3バイト `01101101 01100001 01101110`（ASCIIの「man」）を例に：

1. **連結**して24ビットに：`011011010110000101101110`
2. **4つの6ビットグループに分割**：`011011`、`010110`、`000101`、`101110`
3. **各6ビット値（0〜63）をアルファベット文字に写像**：27→`b`、22→`W`、5→`F`、46→`u`。結果は `bWFu`

3の倍数でない入力はどうなるか。エンコーダーはゼロビットで埋め、不足分を `=` で示します：

- 1バイト余り → 2文字＋`==`
- 2バイト余り → 3文字＋`=`

Base64テキストが `=` や `==` で終わることが多いのはこのためです。パディングは「最後のグループに実際のバイトがいくつあったか」をデコーダーに伝えます。Base64urlなど一部の実装はパディングを省略しても正しくデコードできます——文字列の長さ自体が情報を持っているからです。

## Base64とBase64url：URLセーフ版

標準Base64にはURLやファイル名での問題があります。`+`、`/`、`=` はそこで意味を持つ文字だからです。`+` はクエリ文字列でスペースになり、`/` はパス区切りを壊し、`=` は文脈によって代入と解釈されます。

**Base64url**——[RFC 4648](https://www.rfc-editor.org/rfc/rfc4648)で標準化——は `+` を `-` に、`/` を `_` に置き換え、パディングを省きます。JWTや最近のデータURLで使われるのはこの変種です。ハイフンとアンダースコアを含み、末尾に `=` がないBase64テキストを見たら、それはBase64urlです。

実務ルール：保存やメール的な輸送には標準Base64、URL・クエリパラメータ・トークンにはBase64urlを使う。デコード側は両方受け付けることが多いですが、正しい変種を生成するだけでバグの一クラスが消えます。

## Base64は暗号化ではない

最も根強い誤解なので、独立した節にします。3つの違い：

1. **鍵がない。** 暗号化には秘密鍵が必要。Base64にはない。誰でもデコードできる
2. **定義上可逆。** 暗号化は鍵なしでは不可逆に設計される。Base64は常に誰でも可逆に設計される
3. **目的が違う。** 暗号化は機密性を守る。Base64は*輸送中の整合性*を守る——バイトが壊れないようにするのであって、読まれないようにするのではない

Base64をセキュリティと勘違いすることは現実の脆弱性クラスです。「Base64で保護された」認証情報は、コード、ログ、Basic認証ヘッダーに現れ、誰でもデコードできます。`Authorization: Basic base64(user:pass)` のBase64はHTTP層の輸送儀礼であって、実際の保護は下のTLSが担うべきものです。

## 実践での登場場面

**JSON Web Token。** すべてのJWTは `header.payload.signature` で、最初の2つはBase64urlエンコードされたJSONです。[JWTデコーダー](/ja/tools/jwt-decoder/)でデコードしてみれば、JSONテキストからバイナリ安全なトークンを作る仕組みの全体がこのエンコードだと分かります。

**データURL。** `data:image/png;base64,iVBOR...` はバイナリファイルをHTMLやCSSに直接埋め込みます。小さなアセットには便利ですが、文書は同じ33%膨らみ、ブラウザは描画前にデコードしなければなりません。

**APIペイロード。** JSONは生のバイナリを運べないため、画像・証明書・protobufメッセージはJSONオブジェクト内のBase64文字列として運ばれます。REST APIの標準パターンであり、ファイルを受け付けるLLMのツール呼び出しスキーマでも同じです。

**メール（MIME）。** SMTPがテキスト専用だった時代の名残で、添付ファイルはBase64でエンコードされました。レガシーなテキスト経路が残る場所には、このパターンも残ります。

## よくある落とし穴と回避策

**空白と改行。** MIMEの慣例で76文字ごとに折り返すエンコーダーがあります。空白を除去しないデコーダーは折り返し入力を失敗させます。デコード前に除去しましょう。

**UTF-8の扱い。** ブラウザの古典的ミス：`btoa("日本語")` は例外を投げます。`btoa` はLatin-1しか受け付けないからです。正しい手順は、まず文字列をUTF-8バイト列にエンコードしてからBase64を適用する——当サイトの[Base64ツール](/ja/tools/base64-encoder/)がまさにこれです。Python 2時代のコードにも同じバグがあり、「ペイロードの途中で日本語が化ける」事故の多くを説明します。

**テキストのエンコードとバイトのエンコード。** 文字列をBase64化するとき、実際にエンコードしているのは*その文字エンコーディングのバイト列*です。デコーダーが別のエンコーディング（UTF-8対Shift-JIS対Latin-1）を想定すると文字化けします。何をエンコードしたか常に把握しましょう。

**変種の混同。** 標準Base64（`+` `/` `=`）とBase64url（`-` `_` パディングなし）——間違った方でデコードすると「無効な入力」か、パディング境界で静かに壊れたバイト列になります。

## 現場でのBase64デバッグ

Base64ブロブがおかしいときの最速ループ：デコードして、得られたものを見て、期待したものを再エンコードして、diffする。JWTの署名検証失敗は、たいてい署名が壊れているのではなく、ヘッダーやペイロードが間違った変種や文字エンコーディングでデコードされ、バイト列が変わり、署名チェックが失敗しているだけです。まず[JWTデコーダー](/ja/tools/jwt-decoder/)に通し、JSONがきれいなら問題は別の場所にあります。

データペイロードなら、ワークフロー全体を覆う2つで十分です。変換は[Base64エンコーダー／デコーダー](/ja/tools/base64-encoder/)、結果がJSONなら[JSONフォーマッター](/ja/tools/json-formatter/)で検査。どちらもアップロードなし、すべてローカルで動きます。

## 各言語のBase64実装：全プラットフォームにエンコーダーがある

アルゴリズムを自分で書くことはほぼありません——全プラットフォームに実装が同梱されており、バグはその実装間の差異に潜みます：

| 言語 | エンコード | デコード | UTF-8メモ |
|------|-----------|---------|-----------|
| JavaScript（ブラウザ） | `btoa(binaryString)` | `atob(s)` | `btoa` はLatin-1のみ——先にUTF-8バイト列へ |
| Node.js | `Buffer.from(s).toString('base64')` | `Buffer.from(s,'base64').toString()` | UTF-8を正しく処理 |
| Python | `base64.b64encode(b)` | `base64.b64decode(s)` | `str` ではなく `bytes` で扱う |
| Go | `base64.StdEncoding.EncodeToString` | `base64.StdEncoding.DecodeString` | URL版は `URLEncoding` |
| Java | `java.util.Base64.getEncoder()` | `java.util.Base64.getDecoder()` | URL版は `getUrlEncoder()` |
| シェル | `base64`／`openssl base64 -e` | `base64 -d`／`openssl base64 -d` | 76桁折り返しに注意 |

全実装に共通する失敗モード：

1. **バイトではなく文字列をエンコードする。** Python 2では `base64.b64encode("日本語")` が全く別物をエンコードしていました。正しい形は `b64encode("日本語".encode("utf-8"))` です。Python 2/3移行期は二重エンコードや文字化けペイロードの世代を生み、いまもレガシー連携で顔を出します
2. **デコード時の折り返し。** `base64 -d` は空白を許容しますが、厳格なデコーダーは許しません。MIME折り返し入力はデコード前に展開しましょう
3. **変種の不一致。** JWTライブラリはBase64urlを期待します。`+/=` 入りの標準Base64をURL文脈に渡すと `+`→スペースの破損が起きます。常に変種を経路に合わせてください
4. **不正入力での静かな破損。** 一部のデコーダーは不正文字をエラーにせずスキップします——`"abc$def"` が何かにデコードされる。トークンや署名などセキュリティに関わるデコードには、アルファベット外を拒否する厳格なデコーダーを使いましょう

## 性能と代替形式

Base64だけがバイナリ→テキストの選択肢ではありません。33%のオーバーヘッドが痛い場面のための代替が存在します：

- **16進数（Base16）** — 1バイト2文字、オーバーヘッド100%だがデバッグは至極簡単。人間が目視比較する短いダイジェストや鍵に使い、大量データには使わない（SHA-256ダイジェストが慣例的に16進数なのはこのため——[ハッシュガイド](/ja/blog/sha-256-explained/)参照）
- **Base85（Ascii85）** — 4バイト5文字、オーバーヘッド25%のみ。PDFやPostScriptの内部で使われるが、アルファベットにバックスラッシュや引用符を含むためテキスト文脈では脆い
- **Base32** — 5バイト8文字、オーバーヘッド60%、大文字小文字を区別せず、紛らわしい文字（`0/1`）を除外。人間がタイプするコード向け：ソフトウェアライセンス、TOTPシークレット、リカバリーキー

判断ルールは簡単です。テキストシステム経由の輸送はBase64、URLはBase64url、短く人間が比較する値は16進数、人間がタイプするコードはBase32。それぞれ異なる失敗モードに最適化されており、失敗モードが自分の経路に合うものを選びましょう。
