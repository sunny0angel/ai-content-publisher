Base64 是那种人人都在用、却几乎没人说得清的技术。它出现在 JSON Web Token 里、`data:` URL 里、邮件附件里、API 请求体的中间——而且在每个出现的地方制造同样的困惑：*这是加密吗？是压缩吗？为什么文本会变长 33%？* 答案：Base64 既不是加密也不是压缩。它是一个转换层，让任意二进制数据能在纯文本通道中完好通过，而那 33% 的额外体积就是通行的代价。

本指南讲解 Base64 实际做了什么、逐步拆解编码过程、展示它在真实系统中的身影。要进行正确处理 UTF-8 的转换，用本站免费的 [Base64 编码与解码器](/zh/tools/base64-encoder/)——完全在浏览器内运行。

## 一分钟看懂 Base64

Base64 是一种**二进制转文本编码**：只用 64 个可打印 ASCII 字符表示任意字节。字母表：

```
A–Z（26）＋a–z（26）＋0–9（10）＋「+」「/」（2）＝64 个字符
```

末尾用 `=` 填充。每 3 个输入字节（24 位）变成 4 个输出字符（4×6 位＝24 位），这就是输出总是比输入大约长 33% 的原因——原本 3 个字节的位置现在有 4 个字符。

编码完全可逆且确定：相同字节永远产生相同文本，任何有效的 Base64 文本都能精确还原为原始字节。这种可逆性正是它的本质——也正是 Base64 **不是加密**的原因。只要认得字母表，任何人都能手算解码。

## Base64 为什么存在：文本通道问题

计算机系统对「一个字节意味着什么」的共识少得惊人。字节值 0x89 在 A 处是「PNG 文件头的第一个字节」，在 B 处是「终止字符串的控制字符」，在 C 处是「应该剥离的东西」。为文本设计的通道——JSON 字符串、XML 文档、邮件正文、URL 参数、数据库文本列——都不保证任意字节能完好通过：它们可能拒绝安全范围外的字节、用错误的字符编码重新解释、或在第一个空字节处截断。

Base64 的解法是把每个可能的字节值映射到 64 个「所有文本系统都同意原样放行」的字符上。代价是体积，收益是数据到达时与离开时完全一致。

## 逐位拆解编码过程

以 3 个字节 `01101101 01100001 01101110`（ASCII「man」）为例：

1. **拼接**成 24 位：`011011010110000101101110`
2. **切分成 4 个 6 位组**：`011011`、`010110`、`000101`、`101110`
3. **把每个 6 位值（0–63）映射到字母表字符**：27→`b`、22→`W`、5→`F`、46→`u`。结果：`bWFu`

输入不是 3 的倍数怎么办？编码器用零位补齐，并用 `=` 标记缺口：

- 剩 1 字节 → 2 个输出字符 + `==`
- 剩 2 字节 → 3 个输出字符 + `=`

Base64 文本常以 `=` 或 `==` 结尾就是这个原因——填充告诉解码器最后一组实际有几个字节。Base64url 等现代实现干脆省略填充也能正确解码，因为字符串长度本身已携带信息。

## Base64 与 Base64url：URL 安全变体

标准 Base64 在 URL 和文件名里有麻烦：`+`、`/`、`=` 在那里都是特殊字符。`+` 在查询串里会变成空格，`/` 会打断路径分段，`=` 在某些语境下被当作赋值符。

**Base64url**——由 [RFC 4648](https://www.rfc-editor.org/rfc/rfc4648) 标准化——把 `+` 换成 `-`、`/` 换成 `_`，并去掉填充。JWT 和现代 Data URL 用的都是这个变体。看到带连字符、下划线且结尾没有 `=` 的 Base64 文本，那就是 Base64url。

实用规则：存储和邮件式传输用标准 Base64；URL、查询参数和 token 用 Base64url。解码端通常两者都接受，但生成正确的变体能直接消灭一整类 bug。

## Base64 不是加密

这是最顽固的误解，值得单独一节。三个区别：

1. **没有密钥。** 加密需要密钥，Base64 没有。任何人都能解码
2. **定义上可逆。** 加密被设计为无密钥不可逆。Base64 被设计为对所有人永远可逆
3. **目的不同。** 加密保护机密性。Base64 保护*传输中的完整性*——让字节不被弄坏，而不是不被读到

把 Base64 当安全措施是现实中的一类漏洞：「用 Base64 保护」的凭据出现在代码、日志和 Basic 认证头里，任何人都能解码。`Authorization: Basic base64(user:pass)` 里的 Base64 只是 HTTP 层的传输卫生，真正的保护必须来自底层的 TLS。

## 你在实践中会遇到它的场景

**JSON Web Token。** 每个 JWT 都是 `header.payload.signature`，前两部分是 Base64url 编码的 JSON。用 [JWT 解码器](/zh/tools/jwt-decoder/)解码看看——你会发现整个「从 JSON 文本造出二进制安全 token」的机制就是这种编码。

**Data URL。** `data:image/png;base64,iVBOR...` 把二进制文件直接嵌进 HTML 和 CSS。小资源很方便，但文档会同样膨胀 33%，且浏览器渲染前必须解码。

**API 请求体。** JSON 无法携带原始二进制，所以图片、证书、protobuf 消息以 Base64 字符串的形式在 JSON 对象里传输。这是 REST API 的标准模式，也是许多接受文件的 LLM 工具调用 schema 的做法。

**邮件（MIME）。** SMTP 当年是纯文本协议，附件因此被 Base64 编码。现代邮件在底层依然如此——凡是遗留文本通道存在的地方，这个模式就存在。

## 常见陷阱与规避

**空白与换行。** 有些编码器按 MIME 惯例每 76 字符折行。不先剥掉空白的解码器会在折行输入上失败。解码前先清理。

**UTF-8 处理。** 浏览器经典错误：`btoa("日本語")` 直接抛异常，因为 `btoa` 只接受 Latin-1。正确路径是先把字符串编码为 UTF-8 字节，再套用 Base64——这正是本站 [Base64 工具](/zh/tools/base64-encoder/)的做法。同样的 bug 出现在老 Python 2 代码里，解释了大量「请求体中间的中文乱码」事故。

**编码文本 vs 编码字节。** Base64 编码字符串时，你实际编码的是*其字符编码的字节*。解码方若假设了不同的编码（UTF-8 对 Shift-JIS 对 Latin-1），输出就会乱码。永远清楚自己编码的是什么。

**变体混淆。** 标准 Base64（`+` `/` `=`）对 Base64url（`-` `_` 无填充）——用错的那一边解码，会得到「无效输入」或在填充边界静默损坏的字节。

## 实战调试 Base64

Base64 数据出问题时，最快的循环：解码 → 看结果 → 重新编码预期内容 → diff。JWT 签名验证失败通常*不是*签名坏了，而是 header 或 payload 用错了变体或字符编码解码，字节变了，签名校验自然失败。先把 token 送进 [JWT 解码器](/zh/tools/jwt-decoder/)；如果 JSON 干净，问题在别处。

## 各语言的 Base64 实现：每个平台都自带编码器

你几乎永远不需要自己写算法——每个平台都内置实现，而 bug 就藏在这些实现的差异里：

| 语言 | 编码 | 解码 | UTF-8 提示 |
|------|------|------|-----------|
| JavaScript（浏览器） | `btoa(binaryString)` | `atob(s)` | `btoa` 只支持 Latin-1——先编码为 UTF-8 字节 |
| Node.js | `Buffer.from(s).toString('base64')` | `Buffer.from(s,'base64').toString()` | 正确处理 UTF-8 |
| Python | `base64.b64encode(b)` | `base64.b64decode(s)` | 操作 `bytes` 而非 `str` |
| Go | `base64.StdEncoding.EncodeToString` | `base64.StdEncoding.DecodeString` | URL 版用 `URLEncoding` |
| Java | `java.util.Base64.getEncoder()` | `java.util.Base64.getDecoder()` | URL 版用 `getUrlEncoder()` |
| Shell | `base64` / `openssl base64 -e` | `base64 -d` / `openssl base64 -d` | 注意 76 列折行 |

所有实现共通的失败模式：

1. **编码字符串而不是它的字节。** Python 2 里 `base64.b64encode("日本語")` 编码的是完全错误的东西；正确写法是 `b64encode("日本語".encode("utf-8"))`。Python 2/3 迁移期生产了一整代双重编码或乱码的请求体，至今仍在遗留集成里出现
2. **解码时的折行。** `base64 -d` 容忍空白，严格解码器不。MIME 折行的输入必须先展开再解码
3. **变体不匹配。** JWT 库期待 Base64url；把带 `+/=` 的标准 Base64 放进 URL 语境，`+` 会变成空格。始终让变体匹配通道
4. **非法输入下的静默损坏。** 部分解码器跳过非法字符而不是报错——`"abc$def"` 会被解出点什么而不是报错。安全敏感的解码（token、签名）要用拒绝字母表外字符的严格解码器

## 性能与替代格式

Base64 不是二进制转文本的唯一选项。在 33% 开销吃痛的场景，存在替代品：

- **十六进制（Base16）** — 每字节 2 字符、开销 100%，但调试极简单。用于需要人眼目视比较的短摘要和密钥，避免用于大量数据（SHA-256 摘要惯例用十六进制正是为此——见[哈希指南](/zh/blog/sha-256-explained/)）
- **Base85（Ascii85）** — 每 4 字节 5 字符，开销仅 25%。PDF 和 PostScript 内部使用，但字母表含反斜杠和引号，在文本语境中脆弱
- **Base32** — 每 5 字节 8 字符，开销 60%，大小写不敏感，剔除易混字符（`0/1`）。人类手输代码的选择：软件许可证、TOTP 密钥、恢复码

决策规则很简单：过文本系统用 Base64，URL 用 Base64url，短且需人眼比较的值用十六进制，人输代码用 Base32。每个变体都为不同的失败模式优化——挑失败模式与你的通道匹配的那个。
