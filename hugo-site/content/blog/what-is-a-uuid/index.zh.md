每个系统里的每条记录，都需要一个永不冲突、不需要中心注册、也不会泄露多余信息的「名字」。UUID 就是这个名字——一个 128 位的标识符，任何机器都可以随时独立生成，不必询问任何人。它是现代分布式系统的默认主键，也是数据库、日志、API 响应和移动推送通知里那些 ID 的底层格式。

## UUID 的结构

UUID 是 128 位的值，惯例写作五组共 36 个字符：`xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx`。版本号编码在第三组的第 13 个十六进制位上——`...-4xxx-...` 表示版本 4，`...-7xxx-...` 表示版本 7。格式最初由 [RFC 4122](https://www.rfc-editor.org/rfc/rfc4122)（2005 年）定义，[RFC 9562](https://www.rfc-editor.org/rfc/rfc9562)（2024 年）接替并新增了版本 6、7、8。

活跃使用的版本：

| 版本 | 生成方式 | 排序性 | 典型用途 |
|------|---------|--------|---------|
| 1 | 时间戳 + MAC 地址 | 时间有序 | 遗留系统 |
| 4 | 122 位随机数 | 随机 | 大多数应用的默认选择 |
| 7 | Unix 毫秒时间戳 + 随机数 | 时间有序 | 数据库主键 |

版本 3 和 5（基于名字，MD5/SHA-1）用途不同：它们从名字派生出**确定性的** UUID，相同输入永远得到相同 ID。适合内容寻址，但几乎不用于需要逐实体唯一的记录。

## v4：随机默认值

版本 4 将其 128 位中的 122 位设为随机数，共 2¹²² 种取值——约 5.3 × 10³⁶。这段碰撞数学值得记住，因为它能终结一个长久以来的担忧：即便每秒生成 10 亿个 UUID，也要约 8,500 万年才有 50% 的概率发生一次碰撞。随机 UUID 在实践中不会碰撞；它们只会在底层随机数生成器薄弱时出问题，这正是 [UUID 生成器工具](/zh/tools/uuid-generator/)使用 Web Crypto API（`crypto.randomUUID` / `crypto.getRandomValues`）而非 `Math.random()` 的原因。

v4 是正确的默认选择，适用于：

- **API token 与会话 ID** — 随机性隐藏创建顺序，ID 不会泄露账号或会话的创建时间
- **客户端生成的 ID** — 离线创建记录的移动应用和浏览器，需要无需服务器往返的 ID
- **任何对外公开的标识** — URL 里的连续 ID 会暴露你的业务量，v4 UUID 什么都不暴露

## v7：面向数据库的升级

v4 的弱点在数据库内部显现。随机 ID 成为主键后，行会插入到索引的随机位置。对主键索引采用 B 树的 PostgreSQL 和 InnoDB（MySQL）来说，随机插入顺序会造成索引碎片化、加剧写放大，并在规模扩大后显著拖慢插入。UUIDv7 把毫秒级 Unix 时间戳放在高位，解决了这个问题：时间相近的 ID 排序也相近，插入集中在索引末尾——保留 UUID 全部唯一性属性的同时，获得接近顺序写入的性能。

2026 年的实用建议：**新数据库表的主键，在服务端用 v7**。PostgreSQL 可通过 `gen_random_uuid()`（新版本默认返回 v7）或 `uuid-ossp` 扩展的 `uuidv7()` 原生生成。如果你的框架还不支持 v7，用 v4 也没问题——性能差距在数百万行时才显现，而不是数千行，schema 的正确性比过早优化更值钱。

## 不该用 UUID 的场景

UUID 不是免费的。成本真实存在，以下三种场景其他标识符更合适：

1. **大表上的重度顺序扫描。** UUID 16 字节，`bigint` 8 字节。在数 TB 级别的表上，索引大小差异会直接影响内存和 IO。
2. **需要人输入或念出来的标识。** 没有人会对着电话念 UUID。预约码、订单号、错误码应当短且无歧义。
3. **应用层按 ID 排序的查询。** 如果查询依赖 ID 顺序而非时间戳列，优先用 v7；或者干脆加一列 `created_at`，停止从 ID 推导顺序。

## AI / LLM 技术栈中的 UUID

UUID 在现代 AI 基础设施中无处不在，有三个值得了解的模式：

**幂等键。** Stripe 风格的 API 让客户端为每次请求生成一个 UUID，重试时不会重复扣款。LLM 平台用同样的模式：每次请求生成一个 UUID，网络重试就安全了。

**运行与追踪 ID。** 每条 LangChain/OpenTelemetry 风格的追踪、每次 agent 运行、每个批处理作业都有一个 UUID。分布式追踪正是靠跨服务匹配这些 ID 把日志串起来。

**批量文件键。** OpenAI 兼容的批处理作业用平台生成的 ID 引用文件和作业；自建流水线时，为作业 ID 生成 v4 UUID，并发 worker 就不会冲突。

## 完整版本家族：1、3、5、6、8——以及它们为何少被使用

规范里共有八个版本，实际常用的有四个。其余版本值得了解，以便在现实中一眼认出：

- **v1（时间 + MAC）**：原始版本，由时间戳和机器 MAC 地址生成。时间有序，但会泄露生成机器的网络身份——这个隐私缺陷催生了后续版本。老 Java 和 SQL Server 系统（`newsequentialid()` 是 v1 变体）中至今可见。
- **v3 / v5（基于名字）**：从命名空间（DNS、URL、OID、X.500）内的名字派生的确定性 UUID。相同输入永远得到相同输出。新用途优先选 v5（SHA-1）而非 v3（MD5）。杀手级应用是内容寻址与去重——你恰恰希望相同输入映射到相同 ID 的场景。
- **v6（v1 重排）**：保留 v1 的时间戳语义，但为可排序性重新排列位序。几乎没人用——实际用途中 v7 已全面取代。
- **v7（时间戳 + 随机数）**：现代主力，上文已述。毫秒精度让 ID 按创建顺序排序，数据库最喜欢。
- **v8（厂商自定义）**：仅固定版本位，留给自定义格式。想在自己的语义（分片 ID、区域码）嵌进标准兼容外壳时使用。
- **v2（DCE 安全）**：包含本地域与 UID 的历史版本，实际上已废弃。

实践中决策树收敛为两支：**客户端与安全敏感标识用 v4，服务端数据库键用 v7。** 其余都是利基场景。

## UUID 性能：神话与实测

关于 UUID 流传着两种说法，一种属实，一种夸张：

**属实的：随机主键会造成索引碎片化。** B 树索引保持页面有序；随机键的插入落在随机页面，引发页面分裂和索引不均匀增长。规模一大就能测出来——公开基准显示，UUIDv4 的插入吞吐在数千万行级别明显低于顺序键，而 UUIDv7 保持在 `bigserial` 的百分之几以内。机制本身没有争议，随负载变化的只有幅度。

**夸张的：UUID 会让查询急剧变慢。** 按主键点查时，16 字节 UUID 与 8 字节 bigint 的差异很小。真实成本在三处：索引大小（字节数翻倍）、超宽表的连接性能、写密集负载下的插入吞吐。如果表有百万行、流量中等，v4 完全没问题——正确性和可移植性比最后几个百分点的插入速度更重要。

| 键类型 | 大小 | 插入性能 | 信息泄露 | 典型用途 |
|--------|------|---------|---------|---------|
| bigserial | 8B | 最佳 | 创建顺序、业务量 | 内部表、小应用 |
| UUID v4 | 16B | 良好（规模大时碎片化） | 无 | 公开 ID、token、客户端生成 |
| UUID v7 | 16B | 接近顺序写入 | 仅创建时间 | 数据库主键 |

## 迁移到 UUID：实操顺序

新表的话，答案只有一行：`id uuid primary key default gen_random_uuid()`。迁移现有 `bigserial` 表的话，答案通常是：**不要迁移**。运行正常的整数序列表就让它继续运行，迁移风险集中在外部键和假设 ID 为整数的应用代码里。多数「对外 API 暴露 UUID、内部保留整数」的系统采用的实际中间路线，是加法式迁移：

1. **新增 UUID 列**（`uuid` 类型，可空，暂不设默认值），放在现有 ID 旁边
2. **回填数据**：`UPDATE ... SET uuid = gen_random_uuid() WHERE uuid IS NULL`，分批执行避免长时间锁表
3. **加唯一索引**，将列设为 `NOT NULL`，并为新行设置服务端默认值
4. **API 对外暴露 UUID**，外部键内部继续指向整数 ID。外部系统看到稳定且不透明的标识符，内部连接保持快速
5. **仅在必要时**，在后续独立测试过的迁移中把外部键切换到 UUID

「内部整数、外部 UUID」这一模式，是 API 设计之前就已长大的系统的标准答案——不付 schema 转换的索引成本，就能拿到 v4 的安全属性。

## 现实中的 UUID：URL、日志与各语言支持

**URL。** UUID 设计上就是 URL 安全的——只有十六进制字符和连字符，没有需要百分号编码的字符。它们出现在 REST 路径（`/users/019b2f1a-...`）、查询参数和签名链接中。需要养成的一个习惯：处处使用规范的小写形式。大小写混用在技术上等价，但会破坏朴素的相等判断和缓存键。

**日志与追踪。** 在分布式系统里，UUID 的第二重身份是*关联 ID*：在请求边缘生成同一个 ID 并贯穿所有服务，一次 grep 就能把十几个日志流里同一个用户的旅程重新拼起来。OpenTelemetry 将其形式化为 trace ID——128 位，与 UUID 同尺寸，且（在 W3C Trace Context 标准中）与 v4 格式密切相关。如果你的系统还没有追踪，为每个请求生成一个 v4 UUID 并在每个服务里记录，就能以 5% 的成本拿到 80% 的价值。

**每种语言都自带生成器。** 2026 年，这已经不需要第三方库了：

| 语言 | 一行代码 |
|------|---------|
| JavaScript（浏览器 / Node 20+） | `crypto.randomUUID()` |
| Python | `uuid.uuid4()` / `uuid.uuid7()`（3.14+） |
| Go | `github.com/google/uuid` — `uuid.New()` |
| Java | `java.util.UUID.randomUUID()` |
| SQL（PostgreSQL） | `gen_random_uuid()` |

具体到 v7：Python 3.14 新增 `uuid.uuid7()`；较新的 PostgreSQL 的 `gen_random_uuid()` 返回 v7；Go 和 Java 需要标准的第三方库。[UUID 生成器](/zh/tools/uuid-generator/)批量产出 v4——当你需要「什么都不泄露」的标识符时，这是最快的选择。

**用 v5 做确定性 ID。** 内容寻址系统里有一个值得借鉴的模式：不为每份文档存储随机 ID，而是计算 `uuid5(NAMESPACE_URL, canonical_url)`——同一个 URL 在任何机器上、永远产生同一个 ID。去重能力随之免费获得：「我见过这份文档吗」变成「这个 ID 存在吗」。内容指纹、缓存键、幂等导入——一切「希望相同输入产生相同 ID」的场景都适用。

## UUID 安全注意事项

UUID 不是安全机制，但正确选用它是安全设计的一部分：

**不要把安全寄托在「猜不到」上。** v4 UUID 实践中不可猜测——但它是标识符，不是秘密。把「客户端知道 UUID」当作授权的 API，面对日志、Referer 头、浏览器历史造成的枚举与泄露是脆弱的。不透明 ID 必须配合真正的授权检查；UUID 防的只是猜测，而猜测是最弱的攻击。

**避免对外暴露连续或可推导的 ID。** 这类问题的经典漏洞是 IDOR（不安全直接对象引用）：`/invoices/1042` 诱惑人去递增数字，`/invoices/<v4-uuid>` 则让枚举不可行。这是公开 API 采用 UUID 最有力的实践理由，也解释了为什么 v1 的 MAC 泄露严重到足以催生后续版本。

**使用密码学安全的生成器。** `Math.random()` 对标识符不够格——部分浏览器实现下其输出在实践上可预测。用 `crypto.randomUUID()` 和 `crypto.getRandomValues()`。服务端同理：用平台的 CSPRNG，绝不用通用随机函数。

**不要把秘密或多余语义塞进 UUID。** v4 的随机位固定为 122 位；往里面塞用户 ID 或时间戳，只会削减支撑其安全性的随机性。需要嵌入语义时，明确使用 v7（时间戳）或 v8（厂商自定义），或者干脆分成独立字段。

**UUID 绝不该出现的场合。** 当 ID 本身就是持有凭证时——密码重置 token、一次性下载链接、API 密钥——应使用更大、且不长得像记录标识符的随机值（256 位 token）。UUID 向世界宣告「我是 ID」；重置 token 不该做这种宣告。

## UUID vs ULID vs NanoID vs ObjectId

UUID 并非唯一选择。四种替代方案经常出现，而它们之间的差异小到很容易选错：

| 格式 | 大小 / 字母表 | 可排序 | 碰撞模型 | 最佳用途 |
|------|--------------|--------|---------|---------|
| UUID v4 | 128 位，十六进制 | 否 | 随机 | 公开 ID、token |
| UUID v7 | 128 位，十六进制 | 是（毫秒） | 随机 + 时间戳 | 数据库主键 |
| ULID | 128 位，Crockford base32 | 是（毫秒） | 随机 + 时间戳 | 日志、短且可排序的 ID |
| NanoID | 126 位，URL 字母表 | 否 | 随机 | 短且不透明的 ID |
| ObjectId | 96 位，十六进制 | 是（秒） | 时间戳 + 计数器 + 随机 | MongoDB 默认 |

实用判断规则：

- **ULID** 本质上是 UUID v7 换了一身更紧凑、更好看的外衣（26 字符、大小写不敏感、可按文本排序）。当人会在日志或工单里读 ID、又想要时间顺序而不加额外列时，选 ULID
- **NanoID** 赢在紧凑和 URL 友好——它的字母表剔除了易混淆字符（`0/O/1/l/I`）。短码、分享链接、以及一切 36 字符 UUID 显得笨重的用户可见场景，选它
- **ObjectId** 是 MongoDB 的 12 字节格式：4 字节时间戳、5 字节随机、3 字节计数器。扎根 MongoDB 就用它；为跨库可移植性设计则选 v7
- **UUID v7** 仍是关系数据库的最佳默认：标准在轨、2026 年支持广泛、与 UUID 工具生态互通

诚实的总结：要不可猜测用 v4，要数据库键用 v7，要可读日志用 ULID，要短链接用 NanoID。四种格式四种工作，而你最常伸手的那个有[生成器](/zh/tools/uuid-generator/)兜着。
